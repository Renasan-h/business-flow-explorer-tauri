# Business Flow Explorer Tauri版 — 開発ルール

この文書はChatGPTのチャットをまたいで引き継ぐための作業ルールです。具体的な環境構築・コマンドは `docs/development.md`、機能仕様は `docs/SPECIFICATION.md`、直近の進捗と残作業は `docs/HANDOVER.md` を参照してください。

## リポジトリとブランチ

- Tauri版：https://github.com/Renasan-h/business-flow-explorer-tauri
- Web版（参考）：https://github.com/Renasan-h/business-flow-explorer
- 通常開発：`develop_tauri`。正式リリース：`main`。
- リリース時は原則として `develop_tauri` から `main` にPull Requestを作り、確認後にマージする。既存の作業を無断で巻き戻し・上書きしない。
- READMEは利用者向けの製品説明と画面画像に限定し、開発方針、進捗、CI、内部構造は `docs/` に置く。

## チャット再開時

1. `develop_tauri` の最新HEADと変更履歴を取得する。
2. `docs/HANDOVER.md`、`docs/SPECIFICATION.md`、本書、`docs/development.md` を読む。
3. 引き継ぎ資料のHEADと実際のHEADが異なる場合は、コミット差分とファイルを調べ、古い記述をそのまま採用しない。
4. 現在の未完了タスクと受け入れ条件を確認し、明確な「続けて」の指示なら最優先の残作業から進める。
5. 過去のチャット全体を読めたと断言しない。資料にない仕様は、コード・履歴で裏付けを取るか必要な範囲だけ質問する。

## 実装・コミット

- 1コミット1責務を原則とする。ユーザーからフェーズ一括対応の指示があれば、フェーズ内の関連変更をまとめて進める。
- コミットメッセージは既存履歴に合わせて `[BusinessFlowExplorerTauri]変更概要` を先頭とし、本文に変更内容と対象ファイルを日本語で記載する。過去の会話の厳密なフォーマットは未確認のため、履歴とユーザーの最新指示を優先する。
- 不必要なリファクタや無関係なファイル変更を混ぜない。ユーザーが明示していない危険な強制push、履歴改変、削除は避ける。
- 既存のデータ保護、YAML互換性、ネイティブパス検証を維持する。

## 検証とCI

- 変更箇所に応じてTypeScriptビルド、Playwright E2E、Rustテスト、Rust compile check、Windows実機確認を行う。
- 基本コマンドは `docs/development.md` に記載。
- GitHub Actionsのワークフローは現在すべて `workflow_dispatch` のみ。push/PRでの自動実行は行わない。
- 無料枠・請求上限によりジョブが開始しない場合、コードのテスト失敗と区別し「CI未検証」と報告する。
- テスト成功と報告する際は対象コミット、実行コマンドまたはActions run、結果を明記する。過去の成功を新しいコミットの成功として扱わない。
- CIを手動実行する場合は実行コストを考慮し、必要なワークフローを選ぶ。実行不可の場合はローカル検証と未検証項目を明記する。
- 画面画像・GIFは実アプリのキャプチャを優先。Web版から流用した画像はTauri版の実画面と誤認させず、参考画像と明記する。

## 作業報告と引き継ぎ更新

- 完了したこと、未完了のこと、未検証のことを分けて報告する。
- 実装・ドキュメント更新の区切りで `docs/HANDOVER.md` の完了作業、残課題、次アクション、確認済みコミット、CI結果を更新する。
- 引き継ぎ資料に記載したコミットは「確認時点の基準HEAD」として扱う。資料更新コミット自体のSHAと循環参照しないよう、必要なら直前のHEADを記載する。
- ユーザーに同じ経緯を何度も説明させない。資料やGitHubで確認できる情報は自分で調べる。
